# Scanpy and Harmony

The portable implementation accepts 10x directories, ZIP archives containing exactly one matrix, and 10x H5. It performs per-sample QC, optional Scrublet, concatenation, normalization, HVG, PCA, optional Harmony, neighbours, UMAP, Leiden, markers, and guarded annotation.

RNA cell IDs use explicit `cell_id_prefix`. Preserve raw counts in `layers['counts']` and log-normalized full-gene values in `raw`. An annotation profile is valid only when its analysis signature and expected cluster set match exactly.

## The first pass annotates

A candidate run that ends at `Unassigned` is an unfinished stage, not a delivered one. The candidate run exists to produce the evidence you annotate from; annotating is your job in the same pass, not a hand-off to the user.

Annotate by looking the markers up as they are. There is no bundled reference panel and no crosswalk to reuse: a label carried over from another project, from `Notebooks/example_ipf_scanpy.ipynb`, or from a fixed panel is exactly the transplant this workflow forbids. Establish each cluster's identity from its own ranked markers, its canonical lineage markers, and its QC and sample composition, and be able to say which genes carried the call.

1. Run the `scanpy` task. For a new cluster set this is a candidate run, which writes `tables/candidate_annotation_audit.tsv` alongside the marker and UMAP figures. Every cluster there reads `Unassigned` / `pending_annotation_review`: that is the starting state, not a result.
2. Read the audit table and the figures. Work through the clusters and decide a cell type for each, taking the top-ranked markers as the primary evidence and the cluster's size, QC and sample composition as corroboration. Consult external references for a marker you cannot place from knowledge alone. The marker dotplot you read here is the per-cluster fallback, `candidate_cluster_marker_dotplot.png`, whose rows are Leiden clusters: that is the right shape for this step, because the cell types do not exist yet.
3. Write the labels you settled on into `markers.dotplot_markers` and `markers.cell_type_order` in `config/analysis.yaml`, one group per label, so the annotation dotplot, the ordered legend and the reviewed mapping all name the same set. Recall that `markers.*` is outside the analysis signature, so adding panels does not invalidate the candidate run's signature.
4. Record the reviewed mapping with `tools/record_annotation_review.py`: `--worksheet` writes the reviewer worksheet, `--mapping` records a completed one into `config/annotation.yaml`. Placeholder labels are rejected by design. A cluster you genuinely cannot call stays visible as a low-confidence or ambiguous entry in the worksheet and in what you tell the user; it does not get a placeholder label and it does not get an invented one.
5. Re-run as `run_kind: baseline` with `analysis_confirmed: true`. The formal outputs now carry `cell_type` instead of `candidate_cell_type`, and the annotation dotplot and UMAP are the reviewed ones. The dotplot that ships is this baseline's `annotation_marker_dotplot.png`, one row per cell type with the samples pooled inside each row; the candidate's per-cluster `candidate_cluster_marker_dotplot.png` was the evidence step 2 read and is superseded by it. A run whose only dotplot still has clusters on its rows has not finished this step, because rows can only become cell types once the labels exist.
6. Ask the user to confirm the annotation, naming the clusters you consider settled and the ones you consider uncertain, and the markers behind each. That question closes the pass. If the user corrects a label, record the correction and re-run the baseline; if a correction changes the cluster set, it is a new candidate run with a new `ITERATION_ID`.

The profile you record is bound to this run's analysis signature and exact cluster set, so a later parameter change makes it stale and the run refuses it rather than reusing it silently. Cell-type DMR still never consumes an unreviewed table: `NA`, `Unassigned` and `requires_review` remain invalid there, which is why an uncalled cluster has to be resolved rather than parked.

`Notebooks/scanpy_workflow.ipynb` is the implementation, not a copy of one: the DAG's scanpy task runs `run_scanpy_notebook.py`, which writes a parameter sidecar and executes that same notebook through a kernel, so there is one code path rather than a notebook and a batch script that must be kept in step. `Scripts/Scanpy/README.md` documents the full ten-step notebook flow, the verification loop, and the completion standard; `Scripts/Scanpy/Report.md` is the bilingual evidence ledger. `Notebooks/example_ipf_scanpy.ipynb` is a shipped worked example that the DAG never executes — including its reviewed cluster-to-cell-type mapping, which is valid only for that example's exact cluster set and must not be transplanted.
